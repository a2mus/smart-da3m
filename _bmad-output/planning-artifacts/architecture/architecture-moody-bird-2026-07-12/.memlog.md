## Entry 4 — Core Domain Loop (clarified)

The loop is:
1. **Pedagogue (Expert)** prepares an evaluation/test adapted to a grade level
2. **Student** takes the evaluation
3. **System** identifies gaps in the student's learning from the results
4. **AI** proposes a remediation path tailored to the identified gaps
5. **Pedagogue** validates/customizes the remediation path for that student
6. **Student** follows the remediation path
7. **Parent** monitors results and evolution over time

### Key insight
- The Expert is not just a consumer — they are an **author** (evaluations) and a **gatekeeper** (remediation validation). This is a two-sided responsibility.
- The AI is in the loop but **not autonomous** — it proposes, the pedagogue disposes. This is a critical constraint for trust.
- The parent is **read-only monitoring** — no authoring, no direct intervention in the remediation.

### UX pain root cause
(a) — the app logic is clear in Mus's head but never written as a shared contract. Mus wants the architecture to **propose** the appropriate logic and flow. This means the spine must carry a clear domain-model section that the frontend can be rebuilt against.

### Open questions
- Does the loop iterate? (student does remediation → re-evaluated → new gaps?) 
- Is the remediation path a sequence of activities/exercises, or content to consume?
- What does "evolution" mean for the parent — progress through a path, scores over time, gap closure?

## Entry 5 — Codebase reality check (brownfield sweep)

The backend already models the domain richly:
- **Module / Question / KnowledgeAtom** (content.py) — Expert-authored content
- **DiagnosticSession / CompetencyProfile** (diagnostic.py) — adaptive test + mastery tracking
- **RemediationPath / AtomCompletion** (remediation.py) — student pathway
- **PedagogicalAlert / AlertRecipient** (alert.py) — monitoring layer
- **BayesianKnowledgeTracing** + **DynamicDifficultyAdjuster** (engines) — the "intelligence"
- **Passport assessment** — post-remediation re-evaluation (the loop iterates)

### Gaps / divergences found
1. **RemediationEngine uses in-memory dicts** (`self._paths`) while the API also writes DB RemediationPath rows — dual ownership, data loss on restart. Real divergence to fix.
2. **No "AI proposes → pedagogue validates" step exists in code** — the remediation path is auto-created on student request. The loop Mus described (AI proposes, Expert validates) is not implemented.
3. **No explicit domain-loop state machine** — the loop is implicit, scattered across endpoints.
4. **Expert authoring flow unclear** — modules/questions/atoms exist as models but the creation UX is not visible.

## Entry 6 — Key decisions (user answers)

### Decision: Remediation path lifecycle = Option A (validation gate)
The remediation path has an explicit lifecycle:
`DIAGNOSED → PROPOSED → VALIDATED → IN_PROGRESS → COMPLETED`
- AI generates proposed path (atom selection + ordering based on identified gaps)
- Path sits in PROPOSED until pedagogue reviews, tweaks, and approves
- Only after VALIDATED does the student see and start the path

### Decision: The loop iterates on failure
After remediation completes → student takes final test (Passport) for the target competency:
- **Pass** → competency considered mastered, cycle done for that competency
- **Fail** → another remediation path is suggested (back to PROPOSED, new AI proposal, new pedagogue validation)

Full loop:
```
Diagnostic → gaps identified → AI proposes path → Expert validates
→ Student follows path → Passport (final test)
  → Pass: done
  → Fail: new path proposed (loop repeats)
```

## Entry 7 — Hard rule decided

### Decision: DB is single source of truth for domain state; engines are stateless

**Rule**: The database is the sole owner of all domain state (paths, progress, difficulty, mastery, sessions). Engines (BKT, difficulty adjuster, remediation engine, diagnostic engine) are stateless functions — they receive data, compute a result, return it. They never hold domain state in memory between calls. The API layer writes engine results back to the DB.

**Binds**: Every engine in the system (current and future) must follow this pattern.

**Prevents**: Two owners of the same domain data (in-memory vs DB), data loss on restart, divergence across scaled instances, incompatible engine implementations across sessions/developers.

Status: ADOPTED

## Entry 8 — Three decisions locked

### Decision: Expert rejects proposal → send back to AI for regeneration
The Expert is a *reviewer*, not an inline editor. When unsatisfied with a proposal, they send it back to the AI with feedback, and the AI regenerates. The Expert does not manually add/remove/reorder atoms.
- **Binds**: The remediation API needs a "regenerate proposal" endpoint that accepts Expert feedback.
- **Prevents**: Mixed ownership of path composition (Expert manually editing AI output would create ambiguous authorship).

Note: During validation the Expert *can* adjust (per #3 below), but the primary rejection flow is "send back to AI."

### Decision: Abandoned path lifecycle
When a path is abandoned:
1. The path is **saved** (not deleted) for the student — marked `ABANDONED`
2. **Expert is notified** — can then adjust the path or keep it as-is, triggering re-engagement
3. **Parent is notified** — so they can assist/encourage their child
4. The abandoned path can be **retried** later (retired = `ABANDONED`, not terminal)

Full RemediationPath state machine:
```
DIAGNOSED → PROPOSED → VALIDATED → IN_PROGRESS → COMPLETED
                ↑↓                     ↓            ↓
          (AI regenerates          ABANDONED    Passport test
           on Expert feedback)        ↓          PASS → COMPETENCY_MASTERED
                              Expert notified    FAIL → PROPOSED (new proposal)
                              Parent notified
                              → can be retried
```

### Decision: In-app authoring (Expert UI)
Pédagogues author content through in-app tools — create modules, write questions, upload/create atoms (audio-visual, simulation, mind map). This is the V1 target.
- **Binds**: The frontend needs a full Expert authoring surface (module/question/atom CRUD).
- **Prevents**: Dependence on external tools or manual DB seeding for content.

### Decision: Hybrid AI remediation proposal
The AI proposal is a **hybrid**:
1. **Deterministic selection** — rule-based selection of existing atoms based on BKT-identified gaps (fast, predictable)
2. **LLM generation** — a language model reasons about the student's gaps and generates a personalized pedagogical structure (sequence, justification, pacing)
3. **Expert adjustment** — the pedagogue can adjust the LLM's proposal during validation
- **Binds**: Celery queue for async LLM calls; the proposal generation is a background task.
- **Prevents**: Pure-LLM unpredictability and cost; pure-deterministic rigidity.

**Implication**: The proposal generation is **async** (Celery task), not synchronous. The Expert sees a "generating..." state, then the proposal appears for review.

## Entry 9 — Three more decisions locked

### Decision: Offline boundary
The split is confirmed:
- **Offline-capable**: student taking diagnostic (questions pre-fetched, answers queued, synced on reconnect), student consuming cached remediation atoms, parent viewing cached dashboard data
- **Inherently online**: AI proposal generation (LLM via Celery), Expert validation, real-time notifications, Passport scoring
- **Dexie behavior**: write-behind buffer — answers/completions queue offline and sync when reconnected. The diagnostic session resumes on reconnect.

### Decision: Push notifications (WebSocket or SSE)
V1 uses real-time push for instant notification delivery — not polling. Notifications include:
- Proposal ready for Expert validation
- Path abandoned → Expert + Parent
- Passport failed → Expert (new proposal needed)
- Pedagogical alerts (repeated failure, frustration, inactivity)

**Open sub-decision**: WebSocket vs SSE. SSE is simpler for server-to-client push (which is what this is — we don't need bidirectional). Need to verify current FastAPI support before binding.
- **Binds**: A real-time notification transport layer in the architecture.
- **Prevents**: Polling overhead, delayed notifications, inconsistent alert delivery.

### Decision: Parent dashboard data scope
Parent sees ALL of:
- Raw scores over time
- Mastery level changes per competency (NOT_STARTED → ATTEMPTED → FAMILIAR → PROFICIENT → MASTERED)
- Gap closure (weak → strong competencies)
- Time spent / engagement metrics
- **Binds**: Backend must retain full history of: DiagnosticSession results, CompetencyProfile transitions, AtomCompletion records (with time_spent_ms), Passport results, Alert history. No data pruning for V1.
- **Prevents**: Rebuilding the parent dashboard and discovering the backend doesn't expose/retain the needed history.
